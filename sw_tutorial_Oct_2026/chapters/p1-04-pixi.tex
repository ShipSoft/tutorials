\section{Why an environment, and why pixi}

``It works on my machine'' is the oldest problem in shared software. An
analysis depends on Python, ROOT, and everything ROOT depends on; the SHiP
packages add Geant4, GeoModel, Phlex and compilers. Two people with different
versions of any of these can get different results, or none.

\href{https://pixi.sh}{pixi} solves this per project. It installs packages
from conda channels (\texttt{conda-forge} for the general HEP stack,
\href{https://prefix.dev/channels/ship}{\texttt{prefix.dev/ship}} for the SHiP
packages) for each project separately. Nothing is installed system-wide,
nothing needs administrator rights, and every project has exactly the
versions it asks for. Every ShipSoft repository is a pixi
project, and so is the team repository of \cref{ch:team}.

A pixi project is described by two files, and both are committed to git:

\begin{center}\small
\begin{tabularx}{\linewidth}{l L L}
\toprule
 & \file{pixi.toml}, the \emph{manifest} & \file{pixi.lock}, the \emph{lock file} \\
\midrule
written by & you & pixi, never by hand \\
says       & what the project needs: \texttt{root\_base >=6.36} & exactly what was installed:
                                                             every package, version and build, per platform \\
changes    & when you change the requirements & when pixi solves again (\cmd{pixi add}, \cmd{pixi update}) \\
gives      & the recipe & the same environment for everybody, and for CI \\
\bottomrule
\end{tabularx}
\end{center}

\section{pixi on lxplus}
\label{sec:pixicvmfs}

This tutorial runs on lxplus. Plain pixi installs each environment into a
directory \file{.pixi/} inside the project: about a gigabyte for an
environment with ROOT, several for the SHiP simulation. Your lxplus home is
on AFS, whose quota that would exceed. On lxplus SHiP therefore uses a pixi
build published on CVMFS together with the \cmd{pixi cvmfs} extension, which
keeps the environments out of your AFS area.

\begin{exercise}{Set up pixi, once}
\label{ex:pixicvmfs}
Open your shell's start-up file in your editor:
\begin{shell}
vim ~/.bashrc
\end{shell}
and add this line at the end:
\begin{shell}[basicstyle=\ttfamily\scriptsize]
export PATH=/cvmfs/ship-nightlies.cern.ch/pixi/0.72.0-rattlerfs-layers-d5a7568/bin:$PATH
\end{shell}
Save, log out and in again (or open a new terminal), then check:
\begin{shell}
pixi --version                 # pixi 0.72.0
fs lq ~                        # your AFS quota and usage
\end{shell}
Note the AFS usage: it should hardly change during the whole tutorial.
\end{exercise}

On lxplus you use the environment of a project with \cmd{pixi cvmfs}, run
in the project's directory:

\begin{description}[style=nextline]
  \item[\cmd{pixi cvmfs <task or command>}] runs one task, or any command,
    inside the environment and returns: \cmd{pixi cvmfs build},
    \cmd{pixi cvmfs python hello.py}. Use it whenever you can.
  \item[\cmd{pixi cvmfs}] alone opens a shell with the environment active
    until you \cmd{exit}. Convenient for interactive work; leave it before
    you enter the environment of another project, or you get a mixture of
    both.
\end{description}

The commands that only read or change \file{pixi.toml} and \file{pixi.lock}
are plain pixi: \cmd{pixi init}, \cmd{pixi add -{}-no-install},
\cmd{pixi lock}, \cmd{pixi task}, \cmd{pixi workspace}, \cmd{pixi list}.

\begin{pitfall}
On lxplus, never use \cmd{pixi run}, \cmd{pixi shell}, \cmd{pixi install},
or \cmd{pixi add} without \cmd{-{}-no-install}: they install the environment
into \file{.pixi/}, on AFS. If it happened, \cmd{pixi clean} in the project
removes it. Elsewhere, and in CI, \cmd{pixi run <task>} is the ordinary way
to run a task; you will read it in the ShipSoft documentation and in CI logs.
\end{pitfall}

\section{Your first workspace}

\begin{exercise}{A first workspace}
\label{ex:pixifirst}
Next to your git playground:
\begin{shell}
mkdir pixi-playground && cd pixi-playground
git init
pixi init                # writes pixi.toml, .gitignore, .gitattributes
pixi add --no-install python ruff    # solves, writes pixi.lock
pixi cvmfs python --version
\end{shell}
Open \file{pixi.toml}: what did \cmd{pixi add} write into it? Search
\file{pixi.lock} for \texttt{ruff}: which exact version and build did you get?
What does the new \file{.gitignore} keep out of git?
\end{exercise}

\begin{checkpoint}
A Python version printed, and \file{pixi.toml}, \file{pixi.lock},
\file{.gitignore} and \file{.gitattributes} in the directory.
\end{checkpoint}

Try the other way to use the environment, too: \cmd{pixi cvmfs}, then
\cmd{python} inside it, and \cmd{exit}.

\section{Tasks}

Typing the same long commands is error-prone, and the next person will type
them differently. A \emph{task} gives a command a name, stored in the
manifest, so that everybody, including CI, runs exactly the same thing.

\begin{exercise}{Run it, lint it}
\label{ex:pixitasks}
\begin{shell}
vim hello.py             # one line: print("hello")
pixi task add hello "python hello.py"
pixi task add lint "ruff check ."
pixi cvmfs hello         # hello
pixi cvmfs lint          # All checks passed!
pixi task list
git add pixi.toml pixi.lock hello.py .gitignore .gitattributes
git commit -m "feat: hello, with an environment"
\end{shell}
Look at the \texttt{[tasks]} table that \cmd{pixi task add} wrote into
\file{pixi.toml}.
\end{exercise}

\begin{checkpoint}
\texttt{hello} and \texttt{All checks passed!} printed, and one commit with
the five files, but not \file{.pixi/}.
\end{checkpoint}

\begin{note}
Tasks can also take arguments and depend on each other, and a workspace can
have several \emph{environments}, built from \emph{features}, so that a tool
needed for one job does not end up in the others. The team repository of
\cref{ch:team} keeps \texttt{ruff} in an environment of its own that way; the
\texttt{[feature.lint]} and \texttt{[environments]} tables of its
\file{pixi.toml} show how.
\end{note}

\section{Keeping everybody on the same versions}

\begin{description}[style=nextline]
  \item[\cmd{pixi lock}] solves the manifest and writes \file{pixi.lock}.
    Run it whenever you change \file{pixi.toml} by hand, and commit both:
    CI installs with \cmd{-{}-locked}, exactly what \file{pixi.lock} says,
    and fails if the lock no longer matches the manifest.
    \cmd{pixi lock -{}-check} fails if the lock was out of date.
  \item[\cmd{pixi update -{}-no-install}] solves again and moves to newer versions within
    the manifest's ranges. The new \file{pixi.lock} is a change like any
    other: commit it, on its own, so that its effect can be tested and
    reviewed. In the ShipSoft repositories a bot opens such a pull request
    every month (\cref{ch:ci}).
  \item[\cmd{pixi list}] shows the packages and versions of the environment.
\end{description}

\begin{pitfall}
Never edit \file{pixi.lock} by hand, and do not resolve conflicts inside it
(the \file{.gitattributes} that \cmd{pixi init} writes tells git not to
try). If a rebase conflicts on \file{pixi.lock}, take the version of
\texttt{main} (\cmd{git checkout upstream/main -{}- pixi.lock}), run
\cmd{pixi lock} to solve again with your manifest, and \cmd{git add} the
result. Better still: do not change the environment in a pull request that is
about something else.
\end{pitfall}

\section{How the ShipSoft repositories use pixi}

Every repository has a \file{pixi.toml} and a \file{pixi.lock} at its top.
Their channels are the SHiP channel on \texttt{prefix.dev} and
\texttt{conda-forge}.
Building and testing are tasks, chained with \texttt{depends-on}, so that one
command does everything that is needed. From \repo{Shannon}:
\begin{tomlcode}
build = { cmd = "cmake --build build -j8", depends-on = ["configure"] }
install = { cmd = "cmake --install build", depends-on = ["build"] }
test = { cmd = "ctest --test-dir build --output-on-failure", depends-on = ["build"] }
smoke = { cmd = "scripts/smoke.sh", depends-on = ["build"] }
\end{tomlcode}
so \cmd{pixi cvmfs test} configures, builds and tests a fresh checkout.

\begin{itemize}
  \item \textbf{A \texttt{lint} environment} holds the formatting and lint
    tools (\texttt{prek}, \texttt{ruff}, \texttt{clang-format},
    \texttt{codespell}, \texttt{commitizen}, \ldots).
    \cmd{pixi cvmfs lint} checks every file. (A task \cmd{install-hooks}
    installs git hooks that run the same checks at every commit, but they
    call \cmd{pixi run}: on lxplus, run \cmd{pixi cvmfs lint} before you push
    instead.)
  \item \textbf{Other environments} for special jobs, such as \texttt{bench}
    for benchmarks in \pkg{aegir}.
  \item \textbf{A commented-out \texttt{dev} feature} builds a dependency
    from a local checkout, for changing two packages at once (see the
    developer guide of the SHiP documentation). It stays commented out in
    commits, together with the lock-file changes it causes.
  \item \textbf{CI runs the same tasks}, as \cmd{pixi run -{}-locked test}
    on a fresh GitHub machine (\cref{ch:ci}). If \cmd{pixi cvmfs test} passes
    on lxplus with the committed lock file, the build check passes in CI.
\end{itemize}

\begin{levelcheck}
\begin{itemize}
  \can say what belongs in \file{pixi.toml} and what in \file{pixi.lock}, and
       why both are committed;
  \can create a workspace, add packages, and run a command in it with
       \cmd{pixi cvmfs}, without filling your AFS quota;
  \can define tasks, and a second environment from a feature;
  \can keep \file{pixi.lock} in step with \file{pixi.toml}, and update it
       on purpose.
\end{itemize}
\end{levelcheck}

\begin{solution}
The manifests and the plain pixi commands of this chapter (\cmd{init},
\cmd{add -{}-no-install}, \cmd{lock}, \cmd{task add}, task arguments and
\texttt{depends-on}, \cmd{workspace environment add -{}-feature
-{}-no-default-feature}) were checked with pixi~0.72.0, the version on
CVMFS, and 0.82. \cmd{pixi cvmfs} itself exists only on CVMFS and was not
run in the review environment; the booklet assumes it accepts a task or a
command as \cmd{pixi run} does. Do this chapter once on lxplus before the
session.
\end{solution}
